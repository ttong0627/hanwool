# 한울 배송 주소/배차 DB 활용 전략

작성일: 2026-05-27

이 문서는 주소 입력, 행안부 주소 DB 매칭, 배송동 판정, 지도 표시, 순번 배정까지 한울 배송 서비스가 반복해서 따라야 할 기준이다.

## 핵심 결론

행안부 원본 주소 DB는 충분하다. 실수는 원본 부족보다 `주소 문자열`만 믿고 주문을 저장하는 구조에서 발생한다. 주문에는 반드시 행안부 표준키와 매칭 상태를 함께 저장한다.

## 표준 저장 필드

`orders`에는 다음 필드를 주소 검증 결과로 저장한다.

| 필드 | 의미 |
| --- | --- |
| `raw_address` | 사용자가 입력한 원문 주소 |
| `standard_road_address` | 행안부 규격 도로명주소 |
| `jibun_address` | 지번주소 |
| `detail_address` | 동/호수 등 상세주소 |
| `legal_emd` | 법정동 |
| `admin_emd` | 행정동 |
| `service_dong` | 실제 배송 구역 |
| `adm_cd` | 행정구역코드 |
| `rn_mgt_sn` | 도로명관리번호 |
| `bd_mgt_sn` | 건물관리번호 |
| `udrt_yn` | 지하여부 |
| `buld_mnnm` | 건물본번 |
| `buld_slno` | 건물부번 |
| `lat`, `lng` | 지도 표시 좌표 |
| `coord_source` | 좌표 출처: `kakao`, `cache`, `manual` |
| `match_status` | `matched`, `needs_review`, `not_found` |
| `match_score` | 0~1 신뢰도 |

## 매칭 우선순위

1. `address_overrides`: 현장 수동 보정 규칙
2. `nexus_address.buildings`: 도로명 + 건물번호 정확 매칭
3. `nexus_address.jibun_addresses`: 지번주소 매칭
4. `nexus_address.buildings.full_key`: 정규화 문자열 유사도 매칭
5. `address_cache`: 이전 검색 결과 재사용
6. Kakao 좌표 검색: 좌표 보강 및 캐시 저장

## 배송동 판정

배송 가능 동은 `delivery_zones`에서 관리한다. 광주시 동(洞) 단위 18개(`is_active = true`)를 접수 허용동으로 둔다(면·읍 및 능평동·신현동 제외).

- 핵심 4개 동: 경안동, 송정동, 쌍령동, 탄벌동
- 추가 14개 동: 고산동, 매산동, 목동, 목현동, 문형동, 삼동, 양벌동, 역동, 장지동, 중대동, 직동, 추자동, 태전동, 회덕동

법정동과 실제 배송 구역이 다를 때는 `address_overrides.force_service_dong`으로 현장 기준을 우선한다.

> **배송 우선순위(동 순번) 규칙 없음.** 배차(`dispatch_service.py`)는 동 우선순위 없이 주문 수 기준으로 기사에게 균등 분배한다(같은 동은 같은 기사). 배송 순번은 `route_service`가 동 구분 없이 거리(지도 좌표/도로) 기반으로만 매긴다. 어떤 기사 수(1~18)에서도 주문이 있는 모든 동은 누락 없이 배정된다. `delivery_zones.priority` 컬럼은 남아 있으나 배차·순번 결정에는 사용하지 않는다.

## 검토 필요 기준

다음 경우 주문은 저장하되 `match_status = needs_review`로 둔다.

- 주소는 찾았지만 좌표가 없다.
- 건물 본번만 일치하고 부번은 근사값이다.
- 법정동이 배송 가능 구역에 직접 포함되지 않는다.
- 유사도 매칭 신뢰도가 낮다.

다음 경우는 `match_status = not_found`다.

- 로컬 행안부 DB와 캐시에서 주소를 찾지 못했다.
- Kakao 좌표 검색도 실패했다.

## 배차 이력

배차를 실행하면 `dispatch_runs`와 `dispatch_run_items`에 스냅샷을 남긴다.

- 누가 실행했는지
- 몇 명 기사에게 배정했는지
- 총 주문 수
- 60건 이상 분리 검토가 적용됐는지
- 주문별 기사, 순번, 배송동, 좌표

이 이력이 있어야 총관리자가 나중에 배차 판단을 검증할 수 있다.

## 운영 원칙

- 프론트와 모바일은 직접 주소 문자열을 해석하지 않는다.
- 주소 검증은 `/api/v1/addresses/resolve` 또는 주문 저장 API를 통해 백엔드에서만 수행한다.
- 한 번 매칭된 결과는 `address_cache`로 재사용한다.
- 실패/수동보정/근사매칭은 `address_resolution_logs`에 남긴다.
- 주소/상세주소는 개인정보이므로 관리자 이상 화면에서만 상세 로그를 노출한다.

## 기사 수별 추천 배차와 배송순번 규칙

배차는 먼저 기사 수에 맞는 배송동 권역을 추천하고, 이후 각 기사에게 배정된 주문 내부에서 배송순번을 다시 최적화한다. 동 권역 추천은 빠른 현장 배정을 위한 기본값이며, 총관리자는 화면에서 동 칩을 이동해 조정할 수 있다.

### 공통 순번 규칙

- 1~4명 배차 모두 배송순번은 반드시 작동한다.
- 배차 후 각 기사에게 배정된 주문만 묶어 순번을 재계산한다.
- Kakao Mobility 실제 도로거리 행렬이 가능하면 `optimize_route_with_kakao_matrix()` 결과를 우선 사용한다.
- Kakao Matrix API 키가 없거나 호출 실패 시 좌표 기반 `optimize_route()`로 fallback한다.
- 시장 인접 배송지부터 시작하고, 전체적으로 시장에서 성남 방향으로 마무리되는 흐름을 우선한다.
- 바로 옆 배송지를 두고 먼 곳으로 튀는 이동을 줄이기 위해 nearest-neighbor와 2-opt 개선을 적용한다.
- 좌표가 없는 주문은 정상 좌표 주문 뒤로 밀고, 주소 재검증 결과를 남긴다.
- `sequence_source`는 Kakao Matrix 성공 시 `kakao_matrix`, 자동 fallback 시 `auto`, 기사 수동 변경 시 `manual`로 저장한다.

### 1명 배차

- 모든 오늘 배송 주문을 선택 기사 1명에게 배정한다.
- 기사 내부 순번은 전체 주문을 하나의 경로로 보고 자동 최적화한다.
- 18개 동 전체를 한 명이 담당하면 긴 점프가 발생할 수 있으므로, 물량이 많거나 외곽 동이 섞이면 2~4명 분배를 우선 검토한다.

### 2명 추천 구성

- 목적: 중앙권과 서남외곽권을 빠르게 분리해 한 기사 동선이 과도하게 넓어지는 문제를 줄인다.
- 1기사 권역: 경안동, 송정동, 쌍령동, 탄벌동, 역동, 장지동, 태전동, 회덕동, 양벌동
- 2기사 권역: 고산동, 매산동, 목동, 목현동, 문형동, 삼동, 중대동, 직동, 추자동

### 3명 추천 구성

- 목적: 중앙/동측/서남외곽 3권역으로 나눠 기사별 이동 반경을 줄인다.
- 1기사 권역: 경안동, 송정동, 역동, 장지동, 탄벌동, 회덕동
- 2기사 권역: 쌍령동, 양벌동, 태전동, 고산동, 중대동, 직동
- 3기사 권역: 매산동, 목동, 목현동, 문형동, 삼동, 추자동

### 4명 추천 구성

- 목적: 중앙/동북/남동/서남 4권역으로 더 촘촘히 나눠 장거리 점프를 최소화한다.
- 1기사 권역: 경안동, 송정동, 역동, 장지동
- 2기사 권역: 탄벌동, 회덕동, 쌍령동, 양벌동, 태전동
- 3기사 권역: 고산동, 중대동, 직동, 삼동
- 4기사 권역: 매산동, 목동, 목현동, 문형동, 추자동

### 예외와 보정

- 어떤 기사 수에서도 주문 누락은 허용하지 않는다.
- 추천 그룹에 없는 배송동 주문이 들어오면 가장 적은 주문을 가진 기사에게 자동 보정 배정한다.
- 같은 배송동의 주문은 원칙적으로 같은 기사에게 묶어 배정해 동선이 찢어지지 않게 한다.
- 관리자가 화면에서 동 그룹을 수정하면 수정된 `dong_groups`를 실제 배차 기준으로 사용한다.
- 기사 모바일에서 순번을 수동 변경하면 자동 최적화 결과보다 수동 순번을 우선하고 `sequence_source = manual`로 저장한다.
